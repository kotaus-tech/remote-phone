## 1. Решение по стеку

### Android

- Kotlin, Jetpack Compose и Material 3 с собственной тёмной цветовой схемой.
- Camera2 напрямую; MediaProjection — только для режима «Экран»; MediaCodec — для аппаратного кодирования; foreground service — для длительной сессии и постоянного уведомления.
- Разрешения и переходы в настройки ColorOS оформляются отдельными объясняющими шагами. Доступность Camera2 показывается по фактическим возможностям устройства, а не по ожидаемому набору модулей.

### Windows

**Выбор: Electron + React + TypeScript.** Это компромисс в пользу наиболее прямого пути к WebRTC и быстрой итерации интерфейса; Windows-специфичная часть остаётся нативной.

| Критерий | Electron + React/TypeScript — выбран | WinUI 3 / .NET — альтернатива |
|---|---|---|
| Визуальное качество | Полный контроль над компактной Fluent-подобной системой и общими состояниями; единый HTML-макет легко переносится в React. У Electron есть системный материал Mica/Acrylic для окна на Windows 11 22H2 и новее; содержимое останется собственным тёмным интерфейсом. | Наиболее нативные Fluent-контролы, Mica и интеграция с Windows «из коробки». |
| WebRTC | Chromium уже предоставляет `RTCPeerConnection`, видеодекодирование и `RTCDataChannel`; отдельная .NET-обвязка WebRTC не нужна. Это снижает риск на этапе локального соединения. | Для WebRTC понадобится WebView2 либо отдельная нативная библиотека/обвязка. WebView2 всё равно оставляет задачу безопасной передачи видеокадра из движка в виртуальную камеру. |
| Задержка и нативный путь | Веб-рендерер не гарантирует малую задержку сам по себе. Для камеры планируется проверить offscreen-рендеринг на GPU-текстуре и передачу самого свежего кадра в нативный компонент без очереди устаревших кадров. Это технический риск, а не обещание до измерений. | Проще получить нативную оболочку вокруг системных API, но само наличие WinUI не ускоряет WebRTC-медиатракт. Нативный WebRTC-путь потребует большего объёма сложной сборки и интеграции. |
| Нативная камера | Отдельная DLL на C++/MSVC реализует Media Foundation media source и регистрацию виртуальной камеры. UI и видеодекодер не будут изображать виртуальное устройство. | Та же DLL на C++/MSVC всё равно нужна; .NET-оболочка не заменяет COM media source. |
| Сборка и доставка | Один Windows workflow собирает React/Electron, C++-компонент и `Setup.exe`; сборку и удаление проверяем на Windows runner. | Рабочий вариант, но добавляет Windows App SDK/WinUI к уже обязательным C++-компонентам и усложняет путь к WebRTC. |

**Медиатракт Windows:** Chromium WebRTC → отдельное видео-представление → проверяемый GPU shared-texture мост → нативный C++/MSVC media source → Media Foundation virtual camera. Между кадрами не должна накапливаться очередь: при перегрузке сохраняется последний доступный кадр. Если техническая проверка моста не подтверждает приемлемую задержку и корректное восстановление сигнала, этап виртуальной камеры останавливается для пересмотра пути до дальнейшей реализации.

У Electron есть документированные `BrowserWindow.setBackgroundMaterial(...)` и offscreen-рендеринг с GPU shared texture. Shared-texture API помечен как продвинутый/экспериментальный путь и требует нативного модуля; именно поэтому перед его использованием будет отдельный маленький собираемый proof-of-concept и проверка на целевой Windows 11, а не предположение, что API автоматически решает весь тракт.

### Общий транспорт

Для обеих платформ остаётся WebRTC в локальной сети: DTLS-SRTP для медиаданных и отдельный `RTCDataChannel` для команд и телеметрии; без STUN/TURN по исходному ТЗ. Поиск и сопряжение — отдельный этап. До реализации PIN/PAKE фиксируются конкретный проверенный PAKE-протокол, формат рукопожатия и тесты защиты от перебора; PIN не должен попадать в сетевые сообщения.

### Риски и границы решения

1. **Кадр Chromium → Media Foundation.** Проверить совместимость shared texture, форматы кадра, синхронизацию, повторное открытие камеры приложениями и путь «нет сигнала». До этого нельзя заявлять о достижении ≤100 мс.
2. **Системный API виртуальной камеры.** Реализовывать только по актуальному Windows SDK и официальному примеру Microsoft `Windows-Camera/Samples/VirtualCamera`, сверяя каждую декларацию с SDK. Дополнительная проверка — `smourier/VCamSample`. Не использовать DirectShow.
3. **Администраторские права и удаление.** Экземпляр камеры создаётся с областью `CurrentUser`; область `AllUsers` требует администратора и личному сценарию не нужна. Зафиксированный официальный Microsoft sample регистрирует COM media source системно через MSI. Поэтому ранний Setup PoC выполняет только установку/снятие HKLM COM-регистрации с повышением прав; само приложение и тестовый запуск используют обычные права. После ранней проверки отдельно проверить, возможна ли регистрация source только для пользователя без потери активации Frame Server; если да — убрать повышение прав. Удаление обязано снять регистрацию и экземпляр камеры.
4. **Пинование версий.** Версии Electron, Windows SDK, Android Gradle Plugin и зависимостей фиксируются в репозитории перед первым производственным кодом. Обновление — только с зелёной сборкой всех артефактов.

### Ранний proof-of-concept виртуальной камеры — согласованный стоп-гейт

По просьбе пользователя виртуальная камера проверяется раньше основной разработки режима «Веб-камера»:

1. **Этап 2:** собрать и вложить в `Setup.exe` официальный синтетический источник на базе `Windows-Camera/Samples/VirtualCamera`; CI проверяет сборку x64-компонента и установку/удаление регистрации. На физическом ПК проверить, что камера обнаруживается и выдаёт тестовый движущийся кадр.
2. **Сразу после этапа 3 (до основной разработки «Веб-камеры»):** минимальный поток Camera2 → H.264/WebRTC → декодер Windows → native Media Foundation source. Это ограниченный экспериментальный путь, не полный пользовательский режим и не набор ручных контролов. На целевых OPPO Reno 15 и Windows 11 выполнить все четыре критерия из `docs/HARDWARE_TEST.md`.
3. Только после отчёта и отдельного подтверждения пользователя продолжать основную «Веб-камеру». Если любой критерий не пройден, остановить работу, приложить измерения и предложить 2–3 альтернативы с плюсами и минусами. Основные варианты для сравнения: декодирование в нативной части без прохода через WebRTC-рендерер; другой поддерживаемый кодек/путь аппаратного декодирования; иной локальный транспорт при сохранении обязательного шифрования и сопряжения.

**Измерение задержки:** вывести крупный миллисекундный счётчик на отдельном дисплее в поле камеры. Высокоскоростной камерой (240 кадр/с или выше) одновременно снять исходный счётчик и предпросмотр Discord на другом дисплее. Для каждого измерения сравнить показание счётчика в исходной сцене и в принятом кадре; `задержка = разница показаний` (либо `число кадров между событиями / частота записи × 1000 мс`). Провести не менее 30 замеров и записать медиану, 95-й процентиль и максимум, режим 1080p60, кодек, качество Wi-Fi и сборку. Если 240 кадр/с недоступны, использовать видеозапись с максимальной доступной частотой и указать шаг погрешности. Обычный секундомер годится только для предварительной оценки, не для итогового отчёта.

## 2. Дизайн-система

### Визуальный принцип

Спокойный инструмент, а не панель управления самолётом: один главный сценарий на экран, вторичные параметры постепенно раскрываются в «Профи» и «Диагностике». Большой предпросмотр важнее технических метрик. Статусы короткие и понятные; причина и одно следующее действие — рядом с ошибкой.

### Цвета

| Назначение | Токен | Значение |
|---|---|---|
| Основной фон | `фон/основа` | `#0B0E12` |
| Фон окна/экрана | `фон/поверхность` | `#11161C` |
| Карточка | `фон/карточка` | `#171E26` |
| Карточка при наведении | `фон/подъём` | `#1D2630` |
| Разделитель | `граница/тонкая` | `#29333E` |
| Основной текст | `текст/основной` | `#F2F5F7` |
| Вторичный текст | `текст/вторичный` | `#9AA7B5` |
| Акцент действия | `акцент/мята` | `#74E3B2` |
| Предупреждение | `состояние/внимание` | `#F2BE72` |
| Ошибка/остановка | `состояние/ошибка` | `#FF7F83` |

Все поверхности остаются тёмными. Цвет статуса всегда сопровождается текстом или пиктограммой, а не только цветовой точкой.

### Типографика и ритм

- Общий характер шрифта — системный гротеск: Segoe UI Variable на Windows, системный Roboto на Android; общими остаются размеры, насыщенность и интервалы.
- Базовая сетка отступов — 4 px. Основные шаги: 8 / 12 / 16 / 24 / 32 px.
- Заголовок экрана — 28/34 px на Windows и 24/30 sp на Android; основной текст — 14–16 px/sp; подпись — не меньше 12 px/sp.
- Карточки — радиус 18 px; кнопки — 12 px; индикаторы и переключатели — полностью скруглённые.
- Мягкое появление и смена состояния — 160–220 мс. Учитывать системную настройку уменьшения движения.

### Компоненты и поведение

- **Главное действие:** одна заполненная мятная кнопка на экране; «Старт» / «Остановить» не конкурируют с настройками.
- **Статус:** короткая метка плюс пояснение, например «Подключено» / «Картинка идёт с телефона».
- **Режим:** две крупные карточки на Android; вкладки «Экран» и «Веб-камера» на Windows после сопряжения.
- **Параметр камеры:** название, понятное значение и единица, ползунок, выбор «Авто/Вручную», замок. Неподдерживаемое не показывается в основном интерфейсе; причина доступна в «Диагностике».
- **Профи:** раскрывающаяся область ручных настроек; закрыта по умолчанию.
- **Уведомление/ошибка:** одна фраза о причине и одна основная кнопка, без кода ошибки вне «Диагностики».
- **Диагностика:** единственное место для Camera2, RAW, идентификаторов устройств, диапазонов и технических отчётов.

### Адаптация платформ

- Windows: тёмное окно с Mica в заголовочной/фоновой области, тонкая боковая навигация, большие карточки предпросмотра, компактная панель управления; размеры и свободная ширина окна сохраняются.
- Android: те же цвета, отступы, скругления и иерархия; Material 3 с собственной палитрой, крупные зоны касания, корректные системные отступы и прокрутка на небольшом экране.
- Только русский интерфейс и только тёмная тема. Русские строки не обрезаются на масштабе Windows и при увеличенном размере шрифта Android.

## 3. Экраны и сценарии

### Windows 11

1. **Подключение / найденные телефоны:** найденный телефон, состояние сети, подключение и ручной ввод IP; устройств и PIN в истории нет.
2. **PIN:** ввод PIN, показанного на телефоне; понятная ошибка и повторный ввод без раскрытия кода в отчёте.
3. **Экран:** крупный предпросмотр без искажений, кнопки «Назад/Домой/Недавние», качество, полноэкранный режим, «поверх окон», состояние/задержка/кадры в секунду.
4. **Веб-камера:** горизонтальное превью 16:9, выбор модуля, зеркальное отображение, зум, пресеты, «Профи» и краткое состояние телефона; пустой сигнал представлен состоянием «Нет сигнала», а не застывшим кадром.
5. **Настройки:** качество, параметры прокрутки/инверсии, окно и автозапуск с Windows.
6. **Диагностика:** доступность модулей и возможностей Camera2, сведения о соединении и отчёт для отладки.
7. **Системное состояние:** значок в области уведомлений, состояние камеры, остановка и выход — в системной зоне, не отдельная сложная панель.

### Android 16 / ColorOS 16

1. **Первый запуск:** последовательные шаги с объяснением и проверкой результата — уведомления, исключение из энергосбережения, фоновая работа/автозапуск, закрепление в недавних, при необходимости служба специальных возможностей. Каждый шаг открывается отдельно; отсутствие разрешения даёт конкретное предупреждение.
2. **Главная:** две карточки «Экран» и «Веб-камера», одна кнопка «Старт», состояние соединения; тумблер управления с ПК показывается только для «Экрана» и по умолчанию выключен.
3. **PIN и активный сеанс:** крупный временный PIN, ожидание/подключение, состояние захвата и кнопка остановки; постоянное уведомление также содержит действие «Остановить».
4. **Настройки:** состояние фоновой работы, качество и пояснения по разрешениям; минимум технических пунктов.
5. **Диагностика:** фактически открываемые через Camera2 модули, группы физических камер, диапазоны и поддерживаемые ручные возможности; неподдерживаемое указано честно.

## 4. Интерактивный макет

Открыть [`docs/prototype/index.html`](prototype/index.html). В макете переключаются платформы и экраны; можно пройти демонстрационное сопряжение, запустить/остановить условную сессию, выбрать режим телефона, раскрыть «Профи» и переключить состояние «Нет сигнала». Данные и действия демонстрационные — макет не подключается к камере, сети, Camera2 или Media Foundation.

## 5. Основания и документы для реализации

- Microsoft: [`MFCreateVirtualCamera`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-mfcreatevirtualcamera) и [`IMFVirtualCamera`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nn-mfvirtualcamera-imfvirtualcamera). Декларации API и требования будут сверены с установленным Windows SDK непосредственно перед кодом.
- Microsoft: [официальный пример виртуальной камеры](https://github.com/microsoft/Windows-Camera/tree/master/Samples/VirtualCamera); дополнительный пример, заданный в ТЗ: [`smourier/VCamSample`](https://github.com/smourier/VCamSample).
- Electron: [`BrowserWindow.setBackgroundMaterial`](https://www.electronjs.org/docs/latest/api/browser-window), [offscreen rendering](https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering) и [shared texture](https://www.electronjs.org/docs/latest/api/shared-texture). GPU-мост проверяется отдельной сборкой; это не считается уже доказанной совместимостью с Media Foundation.
- WebRTC: [RTCPeerConnection и RTCDataChannel](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API).
- WinUI как альтернатива: [современная структура WinUI 3 и Mica](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windows-app-sdk-app-structure).

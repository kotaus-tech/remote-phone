# Ранний PoC виртуальной камеры Windows

Этот PoC проверяет только установленную синтетическую виртуальную камеру: доступность через Windows Media Foundation, выдачу меняющихся кадров и работу в webcamtests.com, OBS и Discord. Видео телефона, полная функция «Веб-камера» и WebRTC-медиатракт в этот тест не входят.

## Текущее решение

- Основа — зафиксированный официальный [Microsoft Windows-Camera VirtualCamera sample](https://github.com/microsoft/Windows-Camera/tree/master/Samples/VirtualCamera), commit `626f8b19c5f367602f2e89c6b314573d3776c9df`; лицензия MIT сохранена в `native/vendor/Windows-Camera/LICENSE`.
- CLSID media source записывается установщиком в **64-разрядный HKLM**. DLL и host находятся только внутри Program Files. Деинсталлятор закрывает host и удаляет ключ.
- `MFCreateVirtualCamera` использует время жизни `Session` и область устройства `CurrentUser`. Это создание сеансовой камеры через Media Foundation, а не HKCU COM-регистрация; никаких ручных/временных HKCU-регистраций в текущем тесте нет.
- При запуске установленного приложения Electron автоматически запускает `RemotePhone.VirtualCameraHost.exe`; при закрытии приложения host штатно удаляет сеансовую камеру. Пользователю не нужно запускать отдельный сценарий или скачивать native-архив.
- Установщик создаёт `%ProgramData%\Kotaus\RemotePhone\logs` и ACL для SYSTEM, LocalService, NetworkService и Users: каталог доступен пользователям только на чтение, для общего файла журнала разрешены чтение и добавление записей без права подмены. Журнал `VirtualCameraMediaSource.log` доступен службе Frame Server и приложению; записи также идут в `OutputDebugString`. Лог сохраняется при удалении, чтобы результат теста можно было разобрать.
- Первая запись каждого процесса источника должна идентифицировать версию, SHA-256 DLL, PID, имя/путь процесса и путь загруженной DLL. Дальше пишутся этапы активации, выбранный media type, длительность образца, cadence (измеренный интервал запросов) и HRESULT ошибок.
- Media source объявляет NV12 1280×720 и 1920×1080 при 30 и 60 fps. Для совместимости оставлен RGB32 640×480@30. Генератор рисует движущиеся полосы и контрастный шестизначный счётчик; длительность кадра соответствует объявленным 30/60 fps.
- CI собирает Android APK, Windows Setup и Windows native-компоненты; устанавливает Setup в Program Files, проверяет 64-bit HKLM, ACL ProgramData, отсутствие PowerShell-файлов в установке и удаление COM-регистрации. Если Windows runner доступен для Frame Server, native host через Media Foundation перечисляет типы и захватывает несколько кадров NV12 1920×1080@60.

## Аппаратная проверка — только установленный продукт

1. Установить только свежий `Видоискатель-Setup-0.1.0.exe` из зелёного GitHub Actions; подтвердить запрос администратора для per-machine Setup.
2. Запустить приложение и оставить его открытым. На странице «Веб-камера» дождаться состояния «Камера запущена».
3. В webcamtests.com выбрать «Видоискатель — тестовая камера»; подтвердить движение полос и увеличение счётчика.
4. По очереди повторить проверку в OBS и Discord; каждый раз выбирать то же устройство.
5. Закрыть приложения и «Видоискатель»; убедиться, что сеансовая камера остановилась. Для проверки удаления — удалить Setup и проверить отсутствие CLSID в HKLM64.

Подробный чек-лист и поля для фактических измерений находятся в [`HARDWARE_TEST.md`](HARDWARE_TEST.md). Отдельные PowerShell-сценарии, ручное редактирование реестра и скачивание нативного архива для этого теста не применяются.

## История ошибки и границы вывода

В предыдущем эксперименте источник временно регистрировался в HKCU. Frame Server работает в служебном контексте и не видел COM-регистрацию интерактивного пользователя; прежние строки активации могли относиться к тестовому узлу, а браузер/OBS — загрузить старую DLL из Program Files. Поэтому прежние `media_source_activate`/`media_source_initialized`, изображение полос и проверка после запуска не доказали, какую DLL использовали приложения. Два запуска с отдельным HKCU CLSID завершились `IMFVirtualCamera::Start → 0x80070003`; эти тесты прекращены и не повторяются. Причина, установленная пользователем, учтена: актуальный аппаратный PoC выполняется только через HKLM64-регистрацию свежего Setup и установленное приложение.

Пользователь ранее подтвердил, что Discord показывает пустой предпросмотр/бесконечную загрузку, а браузер и OBS не показывали новый счётчик. Это не считается прохождением. Новый PoC принят только после прямого подтверждения пользователя, что движущийся кадр со счётчиком виден в браузере, OBS и Discord. Если не работает только Discord — диагностировать Discord; иначе зафиксировать media type, cadence, HRESULT и журнал ProgramData и остановиться.

## Источники реализации

- [Microsoft `MFCreateVirtualCamera`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-mfcreatevirtualcamera) и [метод `Start`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-imfvirtualcamera-start).
- Официальный Windows SDK и зафиксированный Microsoft sample — основная реализация. В [README `smourier/VCamSample`](https://github.com/smourier/VCamSample) отдельно отмечено, что media source требуется регистрировать в HKLM с повышением, поскольку его загружают разные процессы; HKCU для такого источника не подходит. Это согласуется с установленной причиной прежней ошибки. Пример используется для сверки, не вместо Setup или аппаратного критерия.

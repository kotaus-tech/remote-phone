# Ранний PoC виртуальной камеры — этап 2

Этап 2 проверяет только синтетический источник из официального примера Microsoft: сборку x64 DLL, регистрацию COM-источника и выдачу тестовых кадров в Windows-приложения. Он не принимает видео с телефона, не измеряет задержку и не является реализацией режима «Веб-камера».

- Исходный пример: [`Windows-Camera/Samples/VirtualCamera`](https://github.com/microsoft/Windows-Camera/tree/master/Samples/VirtualCamera); код зафиксирован в `native/vendor/Windows-Camera` на commit `626f8b19c5f367602f2e89c6b314573d3776c9df`.
- Копия лицензии Microsoft MIT находится в `native/vendor/Windows-Camera/LICENSE`.
- Тестовый host использует `MFCreateVirtualCamera`, `MFVirtualCameraLifetime_Session` и `MFVirtualCameraAccess_CurrentUser`; CLSID и атрибуты media source взяты из зафиксированного примера.
- Полный CI [run #37489288700](https://github.com/kotaus-tech/remote-phone/actions/runs/37489288700) (commit `95adf3f`) собрал Setup.exe и нативные компоненты, проверил установку/удаление и упаковку сценария `Run-VirtualCameraPoC.ps1`. Это автоматическая проверка сборки, не аппаратная приёмка.

## Частичный аппаратный результат пользователя (2026-10-06)

- На сайте проверки веб-камеры в браузере выбранная виртуальная камера выдала сине-чёрный тестовый рисунок; пользователь сообщает, что полосы движутся очень медленно. Браузер не указан.
- На скриншоте сайт показывает `Real FPS: 272` (min 267 / avg 272 / max 275). Это значение пока не принимается как фактическая частота камеры: Microsoft sample задаёт режим 640×480 при 30 fps и длительность кадра 333333 тиков по 100 нс (примерно 33,3 мс).
- Медленный сдвиг полос соответствует тестовому генератору Microsoft: в `SimpleMediaStream.h` по умолчанию выбран синий канал, а `SimpleFrameGenerator.cpp` сдвигает рисунок примерно на одну строку в секунду. Это проверяет смену кадров, но не подтверждает плавность видеотракта.
- В Discord камера доступна в списке, но имя устройства отображается с испорченной кодировкой, предпросмотр пустой, а звонок — в бесконечной загрузке. Этот критерий не пройден.
- На целевом ПК нет приложения «Камера» Windows; OBS не проверен. Код завершения/очистка после Enter не подтверждены. Консоль PowerShell показывает искажённый русский текст из native host (`╨в╨╡╤Б╤…`), что отдельно требует исправления.
- Скрипт временно создаёт COM-запись в HKCU и не меняет HKLM. Однако Setup.exe ранее мог оставить системную COM-запись с тем же CLSID; её наличие не проверено. Поэтому тест не доказывает, что Windows Frame Server активировал DLL исключительно через HKCU.

**Вывод:** PoC этапа 2 остаётся незавершённым и не принят. Получение кадра в браузере — частичный успех, но Discord не работает, Windows Camera/OBS и очистка не проверены, а значение FPS противоречит заявленному режиму источника. До разбора несовместимости не начинать live-phone PoC и основную разработку веб-камеры. Результаты и незакрытые проверки также записаны в `docs/HARDWARE_TEST.md`.

## Запуск из архива нативных компонентов

1. Скачать артефакт `Видоискатель-Windows-native-x64` из [run #37489288700](https://github.com/kotaus-tech/remote-phone/actions/runs/37489288700) и распаковать его в отдельную папку.
2. Открыть 64-разрядный PowerShell обычным способом — не от имени администратора — и выполнить из распакованной папки:

```powershell
.\Run-VirtualCameraPoC.ps1
```

Установка Setup.exe для этого теста не нужна. Сценарий создаёт временную регистрацию только в HKCU, запускает host, затем при штатном завершении удаляет запись. Если временная запись уже существует, сценарий отказывается её перезаписывать. После проверки нажать Enter и убедиться, что источник остановлен, исчез из приложений и HKCU-ключ удалён. Если Setup.exe запрашивает повышение, отменить запрос: необходимость администратора ещё не доказана.

## Критерий приёмки этапа 2

Тестовый движущийся кадр должен быть виден в приложении «Камера» Windows и как минимум в одном из Chrome, Edge или OBS; установка/удаление COM-регистрации должны корректно работать. Проблема с Discord должна быть разобрана до перехода к live-phone PoC, поскольку целевой сценарий также требует работы в Discord. Лишь после прохождения этих проверок и отдельного подтверждения пользователя разрешено начинать live-phone PoC. Если критерий не пройден, остановиться, записать HRESULT, выбранный формат/частоту и поведение каждого приложения, затем выбрать один из вариантов диагностики/исправления.

## Варианты после текущего сбоя

1. **Диагностировать текущий Microsoft source в первую очередь.** Зафиксировать запрошенный приложением media type, формат NV12/RGB32, размер/частоту, временные метки и HRESULT; отдельно проверить Discord после добавления быстрого встроенного счётчика кадров. Плюс — минимальный отход от уже собранного официального примера. Минус — Discord может требовать другой набор форматов или поведение захвата, которое простой тестовый источник не поддерживает.
2. **Собрать сравнительный тест по `smourier/VCamSample`.** Сохранить те же тестовые кадры и проверять те же приложения, чтобы отделить ошибку текущего источника от регистрации/активации Media Foundation. Плюс — независимая реализация для сравнения. Минус — дополнительный нативный код, проверка лицензии и новая поверхность совместимости.
3. **Сделать отдельный минимальный Media Foundation source с явным набором стандартных режимов и корректным расписанием кадров.** Плюс — контроль над форматами/таймингом и возможность адресно отвечать на требования Discord. Минус — больше кода и риска, поэтому это не начинать без выбора пользователя после оценки первых двух вариантов.

До выбора одного направления и повторного зелёного CI никаких изменений в основном видеотракте не вносить.

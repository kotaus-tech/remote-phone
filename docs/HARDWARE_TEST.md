### Шаги на Windows 11 x64

1. Скачать `Видоискатель-Setup-0.1.0.exe` из последнего зелёного CI и установить. Если Windows запросит подтверждение администратора — это ожидаемое действие per-machine установщика.
2. Запустить «Видоискатель» и оставить приложение открытым. Тестовый host автоматически создаёт камеру; на странице **«Веб-камера»** дождаться состояния «Камера запущена».
3. Открыть `webcamtests.com`, выбрать **«Видоискатель — тестовая камера»** и проверить, что кадр меняется, а шестизначный счётчик заметно увеличивается. Если сайт предлагает режимы, записать фактически выбранные разрешение/частоту; его собственное значение FPS не считать измерением источника.
4. Закрыть браузер. Открыть OBS, добавить источник захвата видео, выбрать ту же камеру и проверить движение полос и счётчика.
5. Закрыть OBS. Открыть Discord, выбрать ту же камеру в предпросмотре и проверить, что предпросмотр и звонок работают, счётчик движется.
6. Закрыть веб-сайт, OBS и Discord, затем закрыть «Видоискатель». Камера является сеансовой и должна остановиться/исчезнуть из списков после обновления списка устройств. Удаление Setup.exe проверяет очистку HKLM-регистрации; журнал диагностики при удалении сохраняется.

**Журнал:** `%ProgramData%\Kotaus\RemotePhone\logs\VirtualCameraMediaSource.log`. Источник также пишет в `OutputDebugString`. Первая запись экземпляра источника содержит версию и SHA-256 реально загруженной DLL, PID, имя и путь процесса и путь DLL. В журнале далее должны быть `media_source_activate`, `selected_media_type`, `request_sample_cadence` и `stream_stopped` либо HRESULT ошибки. Частота запросов в журнале — измерение источника; цифра веб-сайта сама по себе ею не является.

**Объявленные режимы:** NV12 1280×720, 1920×1080 и 3840×2160 (4K) при 30 и 60 fps; RGB32 640×480 при 30 fps оставлен для совместимости. Длительность образца рассчитывается по выбранной частоте (около 333333 × 100 нс при 30 fps и 166667 × 100 нс при 60 fps). CI перечисляет режимы через Media Foundation и, если Windows runner поддерживает Frame Server, захватывает несколько изменяющихся кадров 4K30. Если hosted runner запрещает `IMFVirtualCamera::Start` с `E_ACCESSDENIED`, CI помечает только захват как пропущенный; это не заменяет аппаратную проверку и не доказывает выдачу кадров.

## Этап 4 — поток живой камеры телефона (CPU-first)

После принятого synthetic-camera PoC основной путь интеграции — `VideoFrame.copyTo → NV12 → shared memory → Media Foundation virtual camera`. Native-часть реализована: Windows host принимает пакетированный NV12 через stdin, а Media Foundation source читает трёхслотовое shared-memory кольцо; есть масштабирование до выбранного режима и резервный синтетический кадр. Desktop-код теперь принимает видео WebRTC, копирует `VideoFrame` в плотный NV12 и передаёт ограниченный поток кадров host-процессу; Android-код создаёт Camera2-видеотрек и защищённо сигнализирует offer/answer/ICE. Зелёный CI run [37703702143](https://github.com/kotaus-tech/remote-phone/actions/runs/37703702143) подтвердил сборку APK, Windows Setup и native-компонентов, но не запуск Camera2 на телефоне, передачу в shared memory или выдачу кадров внешним приложениям; для этого обязательна физическая проверка. Максимальная цель — 4K 3840×2160; сохранены меньшие режимы 720p/1080p и 30/60 fps. Поддержка режима в объявлениях не гарантирует производительность на каждом ПК.

Windows CI собрал host и Media Foundation source, запустил `--cpu-frame-ring-self-test` и прошёл проверку кольца в shared memory, NV12-масштабирования, меток времени и номера последовательности, очистки слотов и 32-байтового заголовка stdin-пакета. Права и создание канала в пространстве имён `Global` в реальном Frame Server, а также получение кадров приложениями OBS/Discord ещё требуют свежего Setup и физической проверки. Desktop-код теперь формирует цепочку `VideoFrame.copyTo → плотный NV12 → 32-байтовый заголовок и данные в stdin host`; добавлены тесты бинарного формата пакета. Ещё нужно проверить сквозной запуск, фактическое разрешение/частоту, пропуски и завершение сеанса.

### Диагностика вылета GPU-пробы

Пользователь сообщил результат Event Viewer: Application Error, событие 1000, модуль `ntdll.dll`, exception code `0xc0000374` (`STATUS_HEAP_CORRUPTION`, повреждение кучи). Это соответствует повреждению памяти и указывает на модуль/код, но конкретную причину подтверждает только анализ стека/дампа. В `ReadbackWorker::OnOK()` и `OnError()` найдены ручные `delete this;`; `Napi::AsyncWorker` освобождает worker после callback, если не включён `SuppressDestruct`, поэтому эти удаления убраны как вероятная причина двойного освобождения.

В Windows CI добавлен повторный lifecycle stress-тест нативного worker: 16 вызовов реального `inspectSharedTexture` с 4K-размером и заведомо неверным NT handle (ошибочный callback), 128 последовательных пар успешного/ошибочного завершения и 64 одновременных worker. Успешный callback тестируется fixture-режимом того же `ReadbackWorker`, не требующим физического GPU. Скрипт также проверяет нативный C/C++-код на ручной `delete this`. Тест прошёл в зелёном [GitHub Actions run 37688517771](https://github.com/kotaus-tech/remote-phone/actions/runs/37688517771) вместе со сборкой APK, Windows Setup и native-компонентов. Media Foundation capture smoke в hosted runner был пропущен с `E_ACCESSDENIED`, поэтому этот run не является аппаратной проверкой выдачи кадров виртуальной камеры.

**Повторная GPU-проба, 2026-10-08:** пользователь сообщил, что тест теперь запускается и успешно завершается; на присланном скриншоте указаны 1280×720, 151 кадр, 127 разных кадров, 30,1 fps, средний D3D11 readback 0,48 мс, максимум 0,8 мс, пропусков 0. Это подтверждает техническое чтение отдельной 720p GPU shared texture в данной попытке без повторения прежнего вылета. Это не тест 4K и не сквозной медиатракт телефона. CPU baseline на тех же условиях пока отсутствует, поэтому преимущество GPU не установлено.

Строка `media_source_error stage=AllocateSample hresult=0xC00D4A3E` (`MF_E_SAMPLEALLOCATOR_EMPTY`) относится к Media Source и не объясняет heap corruption без новых доказательств. Успешная GPU-проба подтверждает только отдельный путь GPU-текстуры/readback, но не производительность либо корректность полного видеотракта.

### Если приложение снова завершится аварийно — порядок проверки

1. Сначала открыть **Event Viewer → Windows Logs → Application** и найти событие **Application Error (1000)** для `Видоискателя` по времени сбоя. Записать faulting application/module, версию, полный exception code и offset. Если Windows создала WER/minidump, сохранить его для анализа стека; не начинать расследование с журнала виртуальной камеры.
2. Затем сопоставить время и PID с журналами приложения в `%ProgramData%\Kotaus\RemotePhone\logs` и диагностическим логом Electron; проверить, какой модуль завершился и на какой стадии.
3. Только после этого проверить `VirtualCameraMediaSource.log` на ошибки Media Foundation. `MF_E_SAMPLEALLOCATOR_EMPTY` сам по себе не считать причиной аварии другого модуля.
4. Для аппаратной проверки использовать только свежий `Setup.exe` из зелёного GitHub Actions. Отдельные native-архивы, PowerShell-сценарии и ручная COM-регистрация не применяются.

GPU shared-texture → D3D11 остаётся необязательным экспериментом. Текущая проба проверяет импорт/чтение отдельной текстуры и CPU-хэширование редких пикселей, но не сравнивает её с CPU-путём и не измеряет сквозную задержку камеры. Рассматривать GPU-мост можно только после одинаковых сравнительных измерений CPU- и GPU-трактов (разрешение, fps, latency, пропуски, нагрузка CPU/GPU и восстановление). Отсутствие GPU-пробы или её ошибка не блокируют основной CPU-first медиатракт.

- [ ] Кнопка «Остановить трансляцию» на Windows останавливает поток, защищённый сеанс сохраняется.
- Отдельно фиксировать: задержка (ориентир 100–150 мс) пока НЕ измерена — не заявлять.

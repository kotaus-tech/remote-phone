**Устройства:** OPPO Reno 15 · Android 16 · ColorOS 16; Windows 11 x64.
**Правило:** физические проверки отмечает пользователь. Зелёный CI не заменяет проверку на этих устройствах; незаполненное поле не считается пройденным.

## Этап 2 — ранний PoC виртуальной камеры Windows (пройден)

**Результат 2026-10-07:** пользователь подтвердил 10/10: синтетический кадр с движущимися полосами и растущим шестизначным счётчиком виден в webcamtests.com, OBS и Discord (включая предпросмотр и звонок). После закрытия «Видоискателя» сеансовая камера остановилась/исчезла. Windows 11 25H2, build 26200.9457; использован Setup из зелёного CI run `37547871094`. Две приложенные фотографии подтверждают вывод webcamtests.com; показание сайта «187 fps» не считаем измерением частоты источника. Режим, версии OBS/Discord и ProgramData-журнал пользователь не прислал — они не нужны для фиксации прохождения PoC.

**Цель этого этапа:** проверить только установленную синтетическую камеру с движущимися полосами и шестизначным счётчиком. Это подтверждает Windows virtual camera PoC, но ещё не камеру телефона и не полную функцию «Веб-камера».

**Аппаратный тест выполняется только свежим `Setup.exe` из зелёного CI и приложениями Windows.** Не скачивать отдельный native-архив, не запускать PowerShell-сценарии и не делать ручную COM-регистрацию. Установщик с повышением создаёт 64-разрядный CLSID в HKLM, ставит DLL в Program Files и готовит общий журнал в ProgramData; удаление снимает HKLM-регистрацию. Повышение требуется только установщику, приложение запускается обычно.

### Шаги на Windows 11 x64

1. Скачать `Видоискатель-Setup-0.1.0.exe` из последнего зелёного CI и установить. Если Windows запросит подтверждение администратора — это ожидаемое действие per-machine установщика.
2. Запустить «Видоискатель» и оставить приложение открытым. Тестовый host автоматически создаёт камеру; на странице **«Веб-камера»** дождаться состояния «Камера запущена».
3. Открыть `webcamtests.com`, выбрать **«Видоискатель — тестовая камера»** и проверить, что кадр меняется, а шестизначный счётчик заметно увеличивается. Если сайт предлагает режимы, записать фактически выбранные разрешение/частоту; его собственное значение FPS не считать измерением источника.
4. Закрыть браузер. Открыть OBS, добавить источник захвата видео, выбрать ту же камеру и проверить движение полос и счётчика.
5. Закрыть OBS. Открыть Discord, выбрать ту же камеру в предпросмотре и проверить, что предпросмотр и звонок работают, счётчик движется.
6. Закрыть веб-сайт, OBS и Discord, затем закрыть «Видоискатель». Камера является сеансовой и должна остановиться/исчезнуть из списков после обновления списка устройств. Удаление Setup.exe проверяет очистку HKLM-регистрации; журнал диагностики при удалении сохраняется.

**Журнал:** `%ProgramData%\Kotaus\RemotePhone\logs\VirtualCameraMediaSource.log`. Источник также пишет в `OutputDebugString`. Первая запись экземпляра источника содержит версию и SHA-256 реально загруженной DLL, PID, имя и путь процесса и путь DLL. В журнале далее должны быть `media_source_activate`, `selected_media_type`, `request_sample_cadence` и `stream_stopped` либо HRESULT ошибки. Частота запросов в журнале — измерение источника; цифра веб-сайта сама по себе ею не является.

**Объявленные режимы:** NV12 1280×720 и 1920×1080 при 30 и 60 fps; RGB32 640×480 при 30 fps оставлен для совместимости. Длительность образца рассчитывается по выбранной частоте (около 333333 × 100 нс при 30 fps и 166667 × 100 нс при 60 fps). CI должен перечислить режимы через Media Foundation и, если Windows runner поддерживает Frame Server, захватить несколько изменяющихся кадров 1080p60. Если hosted runner запрещает `IMFVirtualCamera::Start` с `E_ACCESSDENIED`, CI помечает только захват как пропущенный; это не заменяет аппаратную проверку и не доказывает выдачу кадров.

## Этап 3 — локальное сопряжение и защищённый транспорт

Код локального сопряжения и защиты реализован; его физическая проверка на OPPO и Windows пока не выполнена. Пользователь попросил не делать отдельный ретест Android/Windows-багфиксов: проверить их вместе с текущим крупным этапом живой камеры. Синтетический camera PoC пройден отдельно; его результат не доказывает физическое сопряжение или поток с телефона.

Реализованные ограничения сеанса: одноразовый 8-значный PIN, срок 5 минут, максимум 5 попыток, локальный IPv4, ограничение размера сообщения. Протокол OPAQUE и сетевой формат зафиксированы в [PAIRING_PROTOCOL.md](PAIRING_PROTOCOL.md); PIN не отправляется по сети и не должен попадать в журналы. Следующий защищённый медиатракт остаётся WebRTC DTLS-SRTP для видео и отдельный `RTCDataChannel` для команд; передача экрана/камеры и WebRTC пока не реализованы.

## Этап 4 — поток живой камеры телефона (активный)

PoC виртуальной камеры принят; начинаем встраивать живой поток. Первый технический стоп-гейт — передача GPU shared-texture Electron → D3D11 на том же целевом ПК. После появления следующего Setup из зелёного CI:

1. Установить Setup и запустить «Видоискатель». На странице «Веб-камера» нажать **«Запустить проверку»** в карточке «Техническая проверка GPU-моста».
2. Дождаться итогового состояния. Для раннего gate приложение должно открыть настоящий GPU shared texture в D3D11, обработать не менее 20 кадров и обнаружить не менее 10 разных кадров. Диагностика копирует текстуру в D3D11 staging-ресурс и считывает разреженную сетку пикселей только для хэширования. FPS, среднее/максимальное время readback и число пропусков — диагностические измерения, а не доказательство задержки полного видеотракта.
3. Если тест вернул ошибку, остановиться и прислать скриншот карточки вместе с моделью GPU (из «Диспетчер устройств → Видеоадаптеры») и версией/сборкой Windows. CPU-bitmap fallback включать нельзя: это не считается прохождением обязательного GPU gate.

После прохождения gate продолжить передачу Camera2-видео с телефона по локальному WebRTC DTLS-SRTP и вывод в установленную Windows virtual camera. Сигнализация остаётся зашифрована уже реализованным OPAQUE/SIGNAL транспортом; STUN/TURN, звук, запись и сохранение кадров не добавлять. Физические проверки Android Camera2 и Windows потока объединить в следующую проверку крупного этапа; при обычном сбое остановиться с измерениями, а если не работает только Discord — диагностировать Discord отдельно.

# Локальное сопряжение и защищённый транспорт

**Статус на 2026-10-08:** профиль OPAQUE и wire-format зафиксированы. В `native/pairing-core` реализованы временное PIN-сопряжение, строгая проверка кадров, transcript, взаимные подтверждения и AEAD для SIGNAL. Ранее полный locked CI [run #37477097263](https://github.com/kotaus-tech/remote-phone/actions/runs/37477097263), commit `bbe4cd2`, подтвердил baseline APK, Windows DLL и `Setup.exe`; Windows-проверка установки/удаления прошла. Целевые RFC 9807-векторы, негативные тесты кадров и профиль Argon2id проверены автоматически; результаты ниже. Новый этап добавляет защищённую v1-сигнализацию SDP/ICE, Android Camera2/WebRTC sender и desktop WebRTC receiver с CPU-путём `VideoFrame.copyTo → NV12 → shared memory`. Кодовые изменения ещё должны пройти CI; **физическое сопряжение и сквозная передача на OPPO Reno 15 и Windows 11 не проверены**. PIN не передаётся по сети, аудио и захват экрана не добавлены. WebRTC-медиаданные должны идти по DTLS-SRTP, отдельный `RTCDataChannel` пока не принимает ввод или текстовые команды.

## 1. Цели и границы

- Соединение только между Android-телефоном и Windows-ПК в одной локальной сети; облака, учётных записей, сохранённых устройств, STUN и TURN нет.
- Телефон — сторона OPAQUE-сервера и показывает временный PIN. ПК — сторона OPAQUE-клиента и вводит PIN с телефона.
- Сетевой наблюдатель может перехватывать, повторять, менять и задерживать пакеты. Он не должен получить PIN, подменить собеседника, перебрать код без ограничений или изменить согласование WebRTC незаметно.
- Скомпрометированные ОС/процессы и физический доступ к разблокированному телефону находятся за границами этой защиты.

## 2. Зафиксированный PAKE и криптографический профиль

Используется **OPAQUE по RFC 9807**. Это спецификация IRTF/CFRG с консенсусом CFRG, опубликованная как Informational RFC, а не Internet Standards Track. Собственный PAKE, обмен PIN в открытом виде и автоматический откат на другой алгоритм запрещены.

| Параметр | Выбор |
|---|---|
| Реализация | общий Rust-core на обеих платформах; зависимость Cargo `opaque-ke = "=4.0.1"`, точная версия зависимостей фиксируется в `Cargo.lock` |
| OPRF | Ristretto255-SHA-512 |
| AKE | OPAQUE-3DH / TripleDH на Ristretto255 |
| Hash / KDF / MAC OPAQUE | SHA-512 / HKDF-SHA-512 / HMAC-SHA-512 |
| KSF | Argon2id, версия 0x13, `m = 65 536 KiB`, `t = 3`, `p = 4`, соль из 16 нулевых байтов, выход `Nh = 64` байта |
| Идентификаторы | клиент `remote-phone/windows`; сервер `remote-phone/android`; идентификатор записи включает случайный `session_id` |
| Контекст login OPAQUE | ASCII `remote-phone/pairing/v1/` || 16-байтовый `session_id` |

Профиль Argon2id — вариант RFC 9106 для памяти-ограниченных устройств (64 MiB, 3 прохода, 4 lanes). RFC 9807 также приводит профиль на 2 GiB; его нельзя молча подменять или ослаблять. В CI прогнано по три вычисления с указанными параметрами, солью из 16 нулевых байтов и 64-байтовым входом/выходом. Linux `ubuntu-latest`: [run #37439895601](https://github.com/kotaus-tech/remote-phone/actions/runs/37439895601) — минимум/медиана/максимум 2 997,49 / 3 032,72 / 3 347,31 мс; [run #37440947065](https://github.com/kotaus-tech/remote-phone/actions/runs/37440947065) — 4 409,54 / 4 412,46 / 4 595,67 мс. Заметный разброс показывает, что hosted runner годится для первичной оценки, но не для вывода о задержке на OPPO Reno 15 или целевом Windows-ПК; производительность и пиковую память на устройствах ещё нужно проверить. В реализации KSF задаётся явно (`Argon2id`, версия `0x13`, `argon2::Params::new(65_536, 3, 4, None)`); для соответствия RFC 9807 используются соль из 16 нулевых байтов и вывод длины `Nh`. При неприемлемой производительности/защите остановиться и пересмотреть профиль явно.

`opaque-ke` выбран как одна реализация OPAQUE на обеих платформах, чтобы не поддерживать две независимые реализации протокола. В опубликованной документации crate упоминается аудит NCC Group 2021 года для версии 0.5.0 и включение исправлений начиная с 1.2.0; это **не аудит версии 4.0.1**. Не заявлять, что используемый бинарный код независимо аудирован. До выпуска обязательны проверка исходников/зависимостей, RFC-векторы, негативные тесты ниже и отдельный пересмотр результата; если этот остаточный риск неприемлем, остановиться до независимого аудита.

## 3. PIN и временная запись

1. При явном запуске сеанса Android создаёт CSPRNG-код из **8 десятичных цифр**; ведущие нули допустимы. Код действует 5 минут по монотонным часам Android.
2. Android создаёт случайный 128-битный `session_id` и свежий `ServerSetup` OPAQUE. Пока PIN ещё локально доступен, приложение выполняет регистрацию OPAQUE **внутри телефона**: локально соединяет шаги ClientRegistration и ServerRegistration, не передавая их через сеть. `ServerSetup` и полученная OPAQUE-запись держатся только в памяти на срок этого сеанса; никаких аккаунтов или записей после сеанса не остаётся.
3. ПК получает только информацию о версии/профиле и `session_id`, а пользователь вводит PIN в приложении ПК. PIN передаётся только как локальный аргумент в OPAQUE-библиотеку каждой стороны; в сетевые структуры, журнал, аналитику или диагностику он не включается.
4. На один сеанс допускается не более 5 корректно сформированных первых OPAQUE login-запросов. Каждый такой запрос расходует попытку **до** дорогой криптографической обработки и независимо от последующего завершения рукопожатия; смена IP/сокета не сбрасывает счётчик. После лимита сеанс блокируется до истечения срока; новый PIN появляется только после явного действия на телефоне. Это ограничивает онлайн-перебор одним сеансом величиной не более 5 из 100 000 000 вариантов (при этом остаётся возможность отказа в обслуживании).
5. Разрешено только одно успешное сопряжение за сеанс. По истечении срока, остановке, ошибке лимита или закрытии сеанса запись удаляется из оперативного состояния; секретные буферы по возможности очищаются. PIN и секреты не логируются. Строки UI очищаются после завершения/истечения, насколько это позволяет платформа.

## 4. Транспортный формат и рукопожатие

Поиск устройства — DNS-SD/mDNS в локальной сети; ручной ввод локального IP остаётся резервным способом. Соединение до WebRTC — WebSocket с **бинарными** сообщениями. Ни discovery TXT-запись, ни приветствие не содержат PIN.

Каждый кадр WebSocket имеет заголовок фиксированного размера в сетевом порядке байтов:

```text
magic[4] = ASCII "RVP1"
message_type[1]
session_id[16]
sequence[4] = uint32 big-endian
payload_length[4] = uint32 big-endian
payload[payload_length]
```

`HELLO` payload имеет ровно 5 байт: `version[1] = 0x01`, `profile[2] = 0x0001` (big-endian), `lifetime_seconds[2]` (big-endian, диапазон 1–300). Общий код кадрирования проверяет размер, тип, номер последовательности и эти поля до передачи payload в библиотеку OPAQUE. Заголовок целиком (29 байт) является associated data для зашифрованных сообщений. Общий предел кадра — 256 KiB; до аутентификации OPAQUE payload ограничен 16 KiB. Неизвестная версия/тип, неверный `session_id`, неверная длина, повторный или пропущенный номер последовательности приводят к закрытию соединения. Компрессии нет.

Типы и направление:

| Тип | Направление | Содержимое |
|---|---|---|
| `HELLO (0x01)` | телефон → ПК | версия `1`, профиль `0x0001`, срок жизни в секундах; `session_id` — в заголовке; последовательность `0` |
| `OPAQUE_LOGIN1 (0x10)` | ПК → телефон | сериализованный `opaque_ke::CredentialRequest`; последовательность `0` |
| `OPAQUE_LOGIN2 (0x11)` | телефон → ПК | сериализованный `opaque_ke::CredentialResponse`; последовательность `1` |
| `OPAQUE_LOGIN3 (0x12)` | ПК → телефон | сериализованный `opaque_ke::CredentialFinalization`; последовательность `1` |
| `AUTH_OK (0x13)` | телефон → ПК | серверное подтверждение ключа и transcript; последовательность `2` |
| `AUTH_ACK (0x14)` | ПК → телефон | клиентское подтверждение ключа и transcript, включая тег `AUTH_OK`; последовательность `2` |
| `SIGNAL (0x20)` | обе стороны | зашифрованное согласование WebRTC (SDP/ICE); начинается с последовательности `3` и затем строго возрастает в каждом направлении |

`HELLO` не считается аутентифицированным. OPAQUE выполняется строго в порядке `LOGIN1 → LOGIN2 → LOGIN3`; OPAQUE-сериализации берутся из выбранной версии `opaque-ke`, не реализуются вручную. На login-стадии обе стороны используют одинаковые профиль, `session_id`, контекст и роли; регистрационная запись создаётся телефоном локально и привязывается к тому же `session_id` и идентификаторам сторон. После неуспешного OPAQUE-состояния ответ с успешным ключом не выдаётся.

OPAQUE-клиент и сервер выводят одинаковый `SessionKey`. Для каждой строки контекста вычисляется `PRK = HKDF-Extract-SHA-512(salt = session_id, IKM = SessionKey)`, затем отдельный ключ через `HKDF-Expand-SHA-512(PRK, info, L)`:

```text
K_confirm      = HKDF-Expand-SHA-512(PRK, "remote-phone/v1/confirm", 64)
K_pc_to_phone  = HKDF-Expand-SHA-512(PRK, "remote-phone/v1/signal/pc-to-phone", 32)
K_phone_to_pc  = HKDF-Expand-SHA-512(PRK, "remote-phone/v1/signal/phone-to-pc", 32)
```

`AUTH_OK` — HMAC-SHA-512 на `K_confirm` над `ASCII("RVP1/server-finished\0") || session_id || SHA-512(transcript)`. `AUTH_ACK` использует отдельную метку `ASCII("RVP1/client-finished\0")` и дополнительно включает полученный тег `AUTH_OK`. Transcript — конкатенация точных байтов кадров `HELLO`, `LOGIN1`, `LOGIN2`, `LOGIN3`, включая заголовки. Сигнализация `SIGNAL` защищается ChaCha20-Poly1305 (RFC 8439): направление использует собственный ключ, nonce — 4 нулевых байта || 8-байтовый счётчик сообщения big-endian; весь заголовок кадра — associated data. Заголовок задаётся до шифрования, `payload_length` включает 16-байтовый AEAD-тег. Номер не может повторяться или переполняться; при переподключении создаются новый `session_id`, PIN и ключи. После handoff OPAQUE `SessionKey` и производные ключи остаются внутри общего Rust-core; наружу не выдаются ключевые байты, только результаты проверки и операции над кадрами. PIN временно существует во вводе UI и native-вызове, очищается из UI сразу после handoff и удаляется из памяти best-effort.

**Текущая кодовая реализация WebRTC (сборка и устройство ещё не проверены):** после `AUTH_ACK` стороны обмениваются ограниченными и типизированными v1-сообщениями offer/answer/ICE внутри AEAD-защищённого SIGNAL; разрешены также `bye` и короткие коды ошибки. JSON UTF-8 ограничен 192 KiB, SDP — 160 KiB, ICE-кандидат — 8 KiB, `sdpMid` — 256 байт; каждая сторона принимает не более 128 ICE-кандидатов за сессию. Desktop создаёт локальный `RTCPeerConnection` без STUN/TURN, принимает только видео, копирует `VideoFrame` в NV12 и передаёт кадр в Windows host. Android создаёт только Camera2-видеотрек, применяет предел 3840×2160 и отвечает через WebRTC; аудиотрек и экранный capturer отсутствуют. Согласование SDP/ICE и DTLS fingerprint защищено OPAQUE SIGNAL, а медиаданные WebRTC идут по DTLS-SRTP без дополнительного самодельного шифрования кадров. Создаётся отдельный DTLS-защищённый `RTCDataChannel`, но текст/ввод/команды не принимаются. Это описание кода, а не доказательство рабочего сквозного тракта; CI-сборка и физическая проверка обязательны. Android WebRTC AAR сейчас закреплён как `io.github.webrtc-sdk:android:150.7871.01`; это сторонняя публикация, не официальный Google WebRTC-дистрибутив, поэтому сборку, ABI и поведение нужно отдельно проверить.

## 5. Автоматические проверки и аппаратные испытания

**Результат baseline-реализации (2026-10-06):** полный locked CI [run #37477097263](https://github.com/kotaus-tech/remote-phone/actions/runs/37477097263), commit `bbe4cd2`, зелёный. Прошли тесты Rust-core и desktop job; собраны Android arm64 Rust-библиотека/JNI и debug APK, Windows x64 Rust DLL, нативные компоненты и `Setup.exe`; автоматическая установка/удаление Windows-пакета завершилась успешно. Это подтверждало сопряжение и native-мосты до добавления WebRTC и **не является физической проверкой на OPPO/Windows 11**. Текущий WebRTC/Camera2 этап описан выше и ожидает CI-сборку и аппаратную проверку; зелёный baseline-run не считается проверкой новых изменений.

**Пройдены кодовые проверки общего Rust-core:**

- [x] Официальные RFC 9807 Appendix C векторы для Ristretto255/SHA-512: C.1.1 и C.1.2 (регистрация, KE1/KE2/KE3, export/session keys) и C.2.1 (ответ сервера для фиктивной записи); RFC-векторы используют Identity KSF, production-профиль Argon2id проверяется отдельно.
- [x] Декодер кадров: все усечения корректного кадра, 2 048 случайных входов, 2 048 структурированных заголовков, неизвестные типы, заявленная длина `u32::MAX`, кадр больше лимита и корректный кадр максимального размера; тест подтверждает отсутствие паники и лишней обработки payload до проверок.
- [x] OPAQUE-сообщение больше 16 KiB отклоняется до дорогостоящей OPAQUE/Argon2-обработки.
- [x] Production-профиль Argon2id v0x13, 65 536 KiB, `t=3`, `p=4`, 16-байтовая нулевая соль и 64-байтовые вход/выход выполняется; Linux CI: run #37477097263 — 3 344,50 / 3 395,44 / 3 433,88 мс; run #37439895601 — 2 997,49 / 3 032,72 / 3 347,31 мс; run #37440947065 — 4 409,54 / 4 412,46 / 4 595,67 мс (минимум / медиана / максимум каждого запуска). - [x] PIN/лимит попыток, точный порядок transcript, полный OPAQUE-обмен поверх закодированных кадров, AUTH_OK/AUTH_ACK и защищённый SIGNAL с раздельными ключами направлений; проверяются неверный PIN, повтор/перестановка, чужой `session_id`, повреждённый ciphertext и исчерпание sequence.

**Остаётся проверить на целевых устройствах:**

- [ ] Измерить время и пиковую память Argon2id на OPPO Reno 15 и Windows-ПК. Все значения выше получены на hosted Linux runner и не являются результатом целевых устройств.
- [ ] Физически проверить обнаружение/ручное подключение в одной Wi-Fi сети и без интернета; проверить, что PIN отсутствует в захвате пакетов, журнале и discovery-записях, а смена IP/сокета не сбрасывает счётчик попыток.
- [ ] Проверить неправильный PIN, блокировку лимита, истечение/остановку и очистку временного состояния в установленном APK/Windows-приложении.

Физические сетевые проверки на OPPO Reno 15 и Windows 11 остаются обязательными и будут объединены с текущим этапом: сопряжение в одной Wi-Fi сети, неверный PIN/лимит, истечение кода, очистка после закрытия, отсутствие PIN в захвате трафика/логах и запуск приложения без повышения; затем — фактический Camera2/WebRTC/NV12-поток через свежий Setup. Синтетический camera PoC пройден пользователем и записан в `docs/HARDWARE_TEST.md`; он не доказывает ни физическое сопряжение, ни рабочий Camera2/WebRTC видеопоток.
